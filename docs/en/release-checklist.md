# Release Checklist

[中文](../release-checklist.md)

Run this checklist before every new release. Verify parsing behavior, Android AAR artifacts, consumer ProGuard rules, execution after minification, documentation, and Maven artifacts together.

`Unreleased` in `CHANGELOG.md` contains changes that have not been published. Choose the target version before updating build versions, the Demo version, dependency examples, and bilingual release notes. An existing version number or successful local verification does not mean the changes have been published.

The current stable version is **1.0.5**, with Demo `versionName 1.0.5` / `versionCode 6`. Both modules are published to Maven Central, and public installation documentation uses 1.0.5 coordinates. See the [release notes](release-notes-1.0.5.md) for migration guidance and verification records. Future releases must still complete this checklist.

## 1. Pre-Release Verification Command

```bash
./gradlew \
  :gson-safe-parser-core:testDebugUnitTest \
  :gson-safe-parser-retrofit:testDebugUnitTest \
  :gson-safe-parser-core:testReleaseUnitTest \
  :gson-safe-parser-retrofit:testReleaseUnitTest \
  :demo-app:testDebugUnitTest \
  :demo-app:testReleaseUnitTest \
  :gson-safe-parser-core:lintRelease \
  :gson-safe-parser-retrofit:lintRelease \
  :demo-app:lintRelease \
  :demo-app:assembleDebug \
  :demo-app:assembleRelease \
  --warning-mode=fail
./gradlew verifyMavenLocalPublicationArtifacts \
  -Dmaven.repo.local="$PWD/build/release-verification-m2" --warning-mode=fail
./gradlew releaseToMavenCentral --dry-run --warning-mode=fail
./gradlew writeOsvReleaseRuntimeLockfile --warning-mode=fail
osv-scanner scan source --lockfile build/osv/release-runtime/gradle.lockfile
git diff --check
git diff --cached --check
```

Expected result:
1. core, retrofit, and demo debug unit tests pass.
2. core, retrofit, and demo release unit tests pass.
3. core, retrofit, and demo release lint pass without low-API calls, resource errors, or manifest errors.
4. demo debug and release APKs build, and release uses R8 minify.
5. `publishToMavenLocal` creates core and retrofit AAR publication artifacts.
6. Dokka javadoc.jar is generated offline and does not depend on external package-list URLs.
7. `verifyMavenLocalPublicationArtifacts` reuses the CI checks for AAR, POM, sources, javadoc, and demo release merged ProGuard configuration. It locates artifacts using the actual publication coordinates and Gradle's local repository location from `maven.repo.local` / Maven `settings.xml`; POM and module metadata coordinates must match.
8. `releaseToMavenCentral --dry-run` verifies the remote release task graph, signing task wiring, and `clean` ordering.
9. The OSV dependency vulnerability scan uses the release runtime dependency input generated by `writeOsvReleaseRuntimeLockfile` and reports no release-blocking findings; CI runs the same gate through `google/osv-scanner-action@v2.3.8`.
10. `git diff --check` and `git diff --cached --check` report no whitespace formatting issues.
11. The build emits no Gradle warning, Kotlin warning, or configuration-time classpath resolution warning.

Incremental verification may reuse successful results whose inputs have not changed; distinguish executed tasks from `UP-TO-DATE` results in the handoff. `writeOsvReleaseRuntimeLockfile` regenerates the dependency list every time. Do not reuse an old scan after changing dependencies. Add `--rerun-tasks` only when a full rerun is needed.

The artifact verification command above first runs `publishToMavenLocal` into the specified temporary repository, avoiding overwrites in the usual Maven local cache. A separate manual publication is unnecessary.

## 2. AAR Artifact Checks

Local Maven artifacts are verified by `verifyMavenLocalPublicationArtifacts` and must satisfy:
1. `gson-safe-parser-core-<target-version>.aar` and `gson-safe-parser-retrofit-<target-version>.aar` exist under the current publication coordinates.
2. The main artifact does not fall back to a plain `.jar`.
3. The POM uses `<packaging>aar</packaging>`.
4. The AAR contains `classes.jar`, `proguard.txt`, `META-INF/LICENSE`, and `META-INF/NOTICE`.
5. `sources.jar` and `javadoc.jar` exist, and the javadoc jar contains Dokka `index.html`.
6. The retrofit POM depends on `gson-safe-parser-core` with the same release version.
7. The retrofit POM and Gradle module metadata keep `okhttp 4.12.0` and `okio 3.6.0` dependencies in runtime scope / runtime variant, do not fall back to Retrofit 2.8.1's old transitive baseline, and do not expose them from the api variant.

## 3. ProGuard And Legacy Integration Checks

Before publishing, confirm:
1. core / retrofit AAR `proguard.txt` contains `kotlin.Metadata`, `com.google.gson.GsonBuilder`, and `@SerializedName <fields>`.
2. demo release merged `configuration.txt` contains both demo model keep rules and AAR consumer rules.
3. demo `proguard-rules.pro` keeps only business model rules and does not copy framework rules manually.
4. `docs/en/android-proguard.md` explains the zero-config trial boundary, minimum release configuration, and the `android.enableR8.fullMode=true/false` choice.
5. Install the current `demo-app/build/outputs/apk/release/demo-app-release.apk` on a device or emulator and run Quick Check with zero failures. Record the APK digest, device/API, version, and result. Release JVM tests and `assembleRelease` do not replace execution on Android.
6. Consume the current AARs by Maven coordinates from an independent Android project. Verify dependency resolution, public API compilation, and automatic consumer-rule merging without `project(...)` dependencies or manually copied framework rules.
7. Regression coverage includes observer reentry raw/event isolation, malformed array-entry Map keys, maps that reject null, Retrofit bodies declaring zero length while containing data, and propagation of custom-adapter, cancellation, and transport failures.

## 4. Documentation And Version Checks

Before publishing, confirm:
1. Root `build.gradle.kts` uses the target version, which has not already been published.
2. Demo `versionName` matches the target version, and `versionCode` has been incremented.
3. During candidate preparation, README / Getting Started clearly distinguish the published and candidate versions. After Maven Central publication and successful dependency resolution, switch public installation coordinates to the target version and update the version contract test and supported version in the security policy.
4. Chinese and English docs can link to each other.
5. README links to Getting Started, Compatibility, Configuration, ProGuard, Demo, Troubleshooting, and Release Checklist. Historical release notes remain discoverable through `CHANGELOG.md`; README need not list each one.
6. `docs/compatibility.md` and `docs/en/compatibility.md` list `minSdk 23`, `compileSdk 36`, `JDK 17`, `Kotlin 2.0.21`, `kotlin-reflect 2.0.21`, `Gson 2.13.2`, `Retrofit 2.8.1`, and R8 / ProGuard boundaries.
7. Move the delivered `Unreleased` entries into the target version without rewriting historical release meaning.
8. The target version's bilingual release notes describe behavior fixes, compatibility boundaries, migration requirements, actual verification, and untested scenarios.
9. `docs/release-notes-1.0.3.md` and `docs/en/release-notes-1.0.3.md` keep JSON shape coercion, event reporting, fallback boundaries, and release verification.
10. `docs/release-notes-1.0.2.md` and `docs/en/release-notes-1.0.2.md` keep the transport exception boundary fix, compatibility boundaries, and release verification.
11. `docs/release-notes-1.0.1.md` and `docs/en/release-notes-1.0.1.md` keep the historical stabilization fixes, compatibility boundaries, and release verification.
12. `docs/release-notes-1.0.0.md` and `docs/en/release-notes-1.0.0.md` keep the initial capabilities, compatibility boundaries, and release verification.
13. Bilingual compatibility and troubleshooting docs explain that network or transport read failures return to Retrofit / OkHttp and cannot be hidden with `emptyResponsePolicy`; README retains the relevant guidance.
14. Bilingual compatibility docs cover the network-stack safety baseline, runtime scope, `OkHttp 4.12.0`, `Okio 3.6.0`, `dependencyInsight`, and dependency resolution verification. README need not repeat these details.
15. Examples and comments distinguish normal Retrofit services from direct converter calls; they must not promise SafeParser empty-response events for Unit/Void or HTTP 204/205.

## 5. Before Remote Publication

Before remote publication, confirm the local machine or CI has Central Portal tokens and GPG signing configured. `publishToMavenLocal` does not require signing; `publishToMavenCentral` / `releaseToMavenCentral` require remote publishing credentials and signing.

```bash
./gradlew releaseToMavenCentral
```

After the publication task succeeds, check the deployment in Central Portal, then decide whether to release or drop it. Do not commit tokens, GPG private keys, JKS / keystore files, `signing.properties`, or `release.properties`.
